# v0.10.0 — Production Crawling Engine foundation

## Goal

Move website analysis from a synchronous request into a job-oriented architecture that can scale to thousands of URLs.

## API

POST `/api/crawl-jobs`
```json
{
  "urls": ["https://example.ru", "https://example.org"],
  "maxPagesPerSite": 3,
  "priority": 10
}
```

GET `/api/crawl-jobs`

GET `/api/crawl-jobs/:id`

POST `/api/crawl-jobs/:id/cancel`

## Current implementation

The release contains:
- organization-scoped crawl jobs;
- URL deduplication;
- a 5,000 URL/job limit;
- per-site page limits;
- priorities;
- job lifecycle states;
- progress calculation;
- cancellation;
- a queue port;
- an in-memory queue adapter for local development;
- frontend for creating and monitoring jobs.

## Production wiring

The next deployment step is to replace `InMemoryCrawlQueue` with Redis/BullMQ:
- API creates job;
- one queue item per URL;
- crawler workers consume items;
- website intelligence parses the site;
- results are persisted in PostgreSQL;
- job counters are updated atomically;
- Redis provides progress/retry/backoff.

Do not run the crawler directly inside an HTTP request for bulk workloads.

## Security

Keep the existing Website Intelligence SSRF protections and add:
- DNS rebinding protection at fetch time;
- robots.txt policy;
- per-domain concurrency;
- global request rate limits;
- retry with exponential backoff;
- worker isolation;
- maximum crawl budget;
- content-type and response-size limits.
